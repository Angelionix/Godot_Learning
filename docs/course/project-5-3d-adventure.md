# Проект 5: 3D Приключение

| Курс разработки игр на Godot Engine | Часть 5 из 6 | Godot 4.x | C++/GDExtension + GDScript |
| --- | --- | --- | --- |

## Введение

Переход от двумерной к трёхмерной разработке игр — это не просто добавление лишней координаты. Это фундаментальное изменение мышления: трансформы вместо позиции, кватернионы вместо углов, объёмная физика вместо плоской, камера как активный участник геймплея, а не просто наблюдатель. В 3D каждый объект существует в пространстве с шестью степенями свободы, и это кардинально меняет подход к дизайну персонажа, врагов, окружения и взаимодействия. Если в 2D камера была фиксирована или следовала за игроком по двум осям, то в 3D камера сама по себе становится системой, требующей сложной логики и оптимизации.

Почему C++ особенно важен для 3D? Ответ кроется в вычислительной сложности. Трёхмерная физика, навигация по навигационным сеткам, расчёт столкновений с множеством коллайдеров, обработка анимаций и состояния множества NPC одновременно — все эти задачи требуют значительно больше вычислительных ресурсов, чем их 2D-аналоги. GDScript прекрасно справляется с UI и высокоуровневой логикой, но когда вам нужно обновлять состояния пятидесяти NPC, вычислять пути навигации и обрабатывать столкновения в реальном времени, C++ через GDExtension становится не роскошью, а необходимостью.

Наш проект — 3D приключение от третьего лица. Это жанр, который объединяет в себе все ключевые подсистемы 3D-игры: персонаж с контроллером движения от третьего лица, система камеры с пружинным механизмом и обходом столкновений, NPC с искусственным интеллектом и навигацией по 3D-сетке, система инвентаря и предметов, разветвлённые диалоги, система квестов со сложными условиями, боевая система с хитбоксами и комбо, и наконец, 3D-эффекты с системой дня и ночи. Каждая из этих подсистем имеет свою зону ответственности и свой оптимальный язык реализации: C++ для вычислительно интенсивного кода, GDScript для UI и данных.

В этом проекте мы продолжаем развивать гибридную архитектуру из предыдущего проекта, но теперь C++ играет основную роль. Если в Проекте 4 (Tower Defense) мы переносили подсистемы на C++ для оптимизации, то здесь мы проектируем их на C++ с самого начала. GDScript используется для того, для чего он создан: интерфейс, ресурсы данных, высокоуровневая координация. Такой подход — это реальная практика коммерческой разработки, где выбор языка определяется задачей, а не догмой.

### Цели обучения

1. Спроектировать контроллер персонажа от третьего лица на C++/GDExtension с камер-относительным движением, переменной высотой прыжка и обнаружением земли
2. Реализовать систему камеры с SpringArm3D, сглаживанием, обходом столкновений и кинематографическими переходами через конечный автомат
3. Создать систему NPC с конечным автоматом (Idle, Patrol, Follow, Flee, Attack) и навигацией через NavigationRegion3D/NavigationAgent3D
4. Построить боевую систему с Hitbox3D/Hurtbox3D, комбо-цепочками, уклонением и блоком
5. Разработать систему инвентаря на C++ с HashMap для O(1) доступа, экипировкой через BoneAttachment3D и сериализацией
6. Реализовать разветвлённую диалоговую систему с условными ветками, интеграцией с квестами и триггерами
7. Создать data-driven систему квестов с QuestData/QuestObjective, отслеживанием целей и наградами
8. Построить цикл дня и ночи с изменением освещения, расписанием NPC и вариацией врагов
9. Освоить настройку GDExtension для 3D: SCons, godot-cpp, _bind_methods(), экспорт свойств
10. Организовать архитектуру проекта по слоям: Data (GDScript Resources), Logic (C++ + GDScript Autoloads), Presentation (сцены), Persistence (SaveManager)

### Оценка времени

**50–70 часов** — это самый амбициозный проект в курсе. Рекомендуется сначала реализовать базовый контроллер персонажа и камеру на GDScript, убедиться в работоспособности, затем перенести на C++. Диалоги, квесты и инвентарь можно разрабатывать параллельно, но боевая система должна быть готова до интеграции с NPC AI. День/ночь — финальная подсистема, добавляемая после стабилизации остальных.

### Почему именно 3D Приключение?

3D Приключение — идеальный жанр для изучения C++/GDExtension в 3D по трём причинам. Во-первых, максимальная плотность подсистем: контроллер персонажа, камера, AI, навигация, бой, инвентарь, диалоги, квесты, день/ночь — каждая требует своего подхода к производительности. Во-вторых, чёткая граница C++/GDScript: физика, AI и обработка коллизий — на C++, UI и данные — на GDScript. В-третьих, реальная практика: именно так устроены коммерческие 3D-игры на Godot — гибридная архитектура, где язык выбирается по задаче.

# Глава 1: Геймдизайн

## 1.1 Концепция и видение

**Жанр:** 3D Action-Adventure / Third-Person

**Ключевая фантазия:** «Герой, вступающий в забытый мир» — Игрок прибывает в долину, окутанную тьмой. Деревня на краю леса — последний оплот света. Тёмный Лорд в своей башне насылает нежить, и только путник, готовый сражаться, исследовать и помогать, сможет вернуть свет. Каждый квест — шаг к пониманию происходящего, каждый диалог — фрагмент истории, каждый бой — проверка мастерства.

**Целевая длительность сессии:** 20–40 минут активной игры. За это время игрок успеет исследовать одну зону, выполнить 1–2 квеста, победить несколько врагов и, возможно, найти новый предмет или разблокировать путь. Сессия должна ощущаться завершённой: игрок получил награду, продвинулся в истории и сохранил прогресс.

**Почему этот жанр идеален для изучения C++ в 3D:** 3D Приключение объединяет все ключевые подсистемы, каждая из которых имеет свой «порог производительности». Контроллер персонажа и камера работают каждый кадр — критический путь для C++. NPC AI обновляется каждый кадр для 10–20 агентов — C++ обязателен. Диалоговый UI работает по событиям — GDScript идеален. Эта естественная граница делает урок о выборе языка наглядным: студент видит, где C++ необходим, а где избыточен.

## 1.2 Основный игровой цикл

Основной цикл 3D-приключения строится на петле «исследование → бой → диалог → квест → награда → усиление». Игрок исследует мир, сражается с врагами, общается с NPC, берёт и выполняет квесты, получает награды и усиливает персонажа. Каждый виток этого цикла расширяет доступные области и углубляет понимание истории.

**Краткосрочный цикл (секунды):** Заметить врага → уклониться от атаки → нанести комбо → подобрать лут. Этот микроцикл происходит каждые 10–20 секунд в бою и каждые 30–60 секунд при исследовании (подбор предмета, открытие сундука). Визуальная обратная связь: числа урона, вспышки оружия, эффекты частиц при ударах.

**Среднесрочный цикл (минуты):** Найти NPC → получить квест → выполнить цель (убить 5 гоблинов, найти предмет, добраться до локации) → вернуться за наградой. Каждый квест занимает 5–15 минут, обеспечивая ощущение завершённости. Диалоги добавляют контекст: почему эти гоблины — угроза, что за предмет нужен, кто ждёт игрока в новой локации.

**Долгосрочный цикл (вся игра):** Исследовать все 5 зон → выполнить 5 основных квестов → победить Тёмного Лорда → освободить долину. Прогрессия через экипировку (лучшее оружие → больше урона → доступ к более сложным врагам) и через квесты (новые области → новые NPC → новые задания). Цикл дня/ночи добавляет вариативность: ночью враги сильнее, но и лут лучше.

## 1.3 Персонаж и параметры

Контроллер персонажа — основа 3D-приключения. Персонаж перемещается от третьего лица: ввод интерпретируется относительно камеры, прыжок имеет переменную высоту, уклонение даёт кадры неуязвимости, а боевые комбо требуют управления выносливостью. Все параметры настраиваются через инспектор Godot благодаря экспорту C++ свойств через _bind_methods().

### Таблица параметров игрока

| Параметр | Базовое значение | С улучшениями | Описание |
|---|---|---|---|
| max_health | 100 | 200 | Здоровье, увеличивается предметами-улучшениями |
| max_stamina | 100 | 150 | Выносливость, тратится на спринт, уклонение, комбо |
| move_speed | 5.0 m/s | 5.0 m/s | Скорость ходьбы |
| sprint_speed | 8.0 m/s | 9.5 m/s | Скорость бега, тратит 15 выносливости/сек |
| jump_velocity | 4.5 m/s | 5.5 m/s | Начальная скорость прыжка |
| rotation_speed | 10.0 | 10.0 | Скорость поворота персонажа к направлению движения |
| dodge_speed | 10.0 m/s | 10.0 m/s | Скорость уклонения (0.3 сек, 20 выносливости) |
| light_attack_damage | 10 | 15 | Урон лёгкой атаки |
| heavy_attack_damage | 25 | 35 | Урон тяжёлой атаки, тратит 15 выносливости |
| block_reduction | 60% | 75% | Снижение урона при блоке, тратит 10 выносливости/удар |
| stamina_regen | 25/сек | 35/сек | Восстановление выносливости (не в бою: 40/сек) |

### Формулы боя

**Урон лёгкой комбо-цепочки (3 удара):** `total = light × 1.0 + light × 1.2 + light × 1.5`

При базовом уроне 10: 10 + 12 + 15 = 37 урона за комбо (~1.5 сек). Комбо сбрасывается, если следующий удар не следует в течение 0.6 секунды.

**Урон тяжёлой атаки:** `heavy_damage × weapon_multiplier`

Базовый тяжёлый удар наносит 25 урона, но имеет больший кулдаун (0.8 сек) и тратит 15 выносливости. Эффективен против бронированных врагов.

**Уклонение:** Персонаж движется со скоростью `dodge_speed` в течение 0.3 сек. Первые 0.2 сек — кадры неуязвимости (i-frames). Стоимость: 20 выносливости. Кулдаун: 0.5 сек.

**Блок:** Уменьшает входящий урон на `block_reduction`%. Удар по блоку отбрасывает атакующего. Стоимость: 10 выносливости за заблокированный удар. Блок сбивается при нулевой выносливости.

### Выносливость как ресурс

Выносливость — ключевой стратегический ресурс. Спринт, уклонение, тяжёлые атаки и блок — все тратят выносливость. Игрок должен выбирать: уклониться от атаки (20 выносливости) или заблокировать (10 выносливости)? Нанести тяжёлый удар (15 выносливости) или дождаться комбо? Спринт к врагу (15/сек) или подойти шагом? Менеджмент выносливости — разница между мастером боя и новичком.

## 1.4 Структура мира

Мир состоит из 5 зон, соединённых переходами. Каждая зона имеет уникальную атмосферу, набор врагов и сюжетный квест. Прогрессия через мир ограничена квестовыми предметами: чтобы войти в Руины, нужен ключ от Лесного стража; чтобы попасть в Катакомбы — амулет из Руин; чтобы войти в Тёмную башню — все три артефакта.

## 1.5 Боевая система

Боевая система в 3D-приключении строится на Hitbox3D/Hurtbox3D — 3D-аналоге 2D-паттерна. Hitbox — это Area3D с коллайдером, которая активно наносит урон при пересечении с Hurtbox3D противника. Hurtbox — это Area3D, которая пассивно принимает урон. Разделение слоёв коллизий гарантирует, что Hitbox игрока не пересекается с Hurtbox игрока.

### Типы врагов и боевые характеристики

| Враг | HP | Урон | Скорость | Дальность обнаружения | Поведение | Награда |
|---|---|---|---|---|---|---|
| Гоблин | 30 | 5 | 3.0 m/s | 8m | Патруль → Преследование → Атака ближняя | 10g,偶尔 зелье |
| Волк | 20 | 8 | 5.0 m/s | 12m | Стая (2–4), атака с флангов | 5g |
| Скелет-воин | 60 | 10 | 2.5 m/s | 6m | Патруль → Блок → Контратака | 15g |
| Скелет-лучник | 25 | 8 (стрела) | 2.0 m/s | 15m | Держит дистанцию, стреляет | 12g |
| Призрак | 40 | 15 | 4.0 m/s | 10m | Телепорт, проходит сквозь стены | 20g |
| Скелет-маг | 35 | 12 (магия) | 2.0 m/s | 12m | AOE-заклинание, отступает | 25g |
| Тёмный рыцарь | 100 | 18 | 2.5 m/s | 8m | Блок, тяжёлая атака, комбо | 40g |
| Тёмный Лорд (Босс) | 500 | 25 | 3.0 m/s | — | 3 фазы, уникальные атаки | 200g + артефакт |

### Анализ баланса: время убийства

**Время убийства (базовое оружие, лёгкие комбо):** `time = enemy_hp / (combo_dps × hit_rate)`

При лёгком комбо (37 урона за 1.5 сек) и hit_rate 80%:
- DPS ≈ 37 / 1.5 × 0.8 = 19.7

| Враг | HP | Время убийства | Опасность |
|---|---|---|---|
| Гоблин | 30 | 1.5 сек | Низкая, но в группе (3+) опасны |

Каждый диалог определяется ресурсом DialogueData с массивом DialogueLine. Линии могут содержать choices (варианты ответов), conditions (условия видимости) и on_complete (действия после реплики). Условия проверяются в C++ для скорости: например, `has_item(&"forest_key")` проверяет инвентарь за O(1) через HashMap.

```

├─ "Добро пожаловать, путник..." → [Рассказать о себе] / [Спросить о долине]
│   ├─ [Рассказать о себе] → "Значит, ты прибыл из-за гор..."
│   └─ [Спросить о долине] → "Тёмный Лорд насылает нежить..."
│       └─ [Предложение помочь] → Квест «Очисти лес от гоблинов» (условие: нет активного квеста)
└─ "Возвращайся, когда будешь готов..." (условие: есть активный квест)
```

## 1.8 Инвентарь и экипировка

Система инвентаря — центральная подсистема, которая связывает подбор предметов, торговлю, экипировку и квесты. Логика реализуется в C++ для скорости операций, данные — в GDScript Resources для удобства редактирования.

### Формула итогового урона

`final_damage = (base_attack + weapon_bonus) × combo_multiplier × enemy_defense_factor`

- `base_attack` — лёгкий (10) или тяжёлый (25)
- `weapon_bonus` — бонус от экипированного оружия
- `combo_multiplier` — 1.0 / 1.2 / 1.5 для 1/2/3 удара
- `enemy_defense_factor` — 1.0 для гоблинов, 0.7 для скелетов-воинов (блокируют 30%), 0.5 для Тёмного рыцаря (блокирует 50%)

# Глава 2: Архитектура

## 2.1 Обзор архитектуры (4 слоя)

Архитектура 3D-приключения строится на четырёх слоях, каждый из которых имеет чёткую зону ответственности. Особенность этого проекта — C++ играет основную роль в Logic и Presentation слоях, а GDScript доминирует в Data и Persistence. Это осознанный выбор: C++ обеспечивает производительность для физических подсистем, GDScript — удобство для данных и UI.

**Data Layer (Слой данных):** ItemData, QuestData, QuestObjective, DialogueData, DialogueLine, DialogueChoice, EnemyData, NPCData — все наследуют Resource и используют @export для настройки в редакторе. Никакой логики, только данные. Ресурсы создаются на GDScript для удобства редактирования в инспекторе Godot. C++ код читает эти ресурсы через GDExtension API.

**Logic Layer (Слой логики):** Глобальные менеджеры и C++ контроллеры. GameManager (состояние игры, пауза, регистрация игрока — GDScript Autoload), AdventureCharacter (контроллер персонажа — C++), CameraController (камера — C++), CombatController (бой — C++), NPCController (AI — C++), InventorySystem (инвентарь — C++), QuestSystem (квесты — C++), DayNightCycle (день/ночь — C++), EconomyManager (экономика — GDScript Autoload), AudioManager (звук — GDScript Autoload). Все менеджеры общаются через сигналы, обеспечивая слабую связанность.

**Presentation Layer (Слой представления):** Player, NPC scenes, Enemy scenes, PickableItem, HUD, DialoguePanel, InventoryUI, QuestLogUI, CraftingPanel — все визуальные компоненты. Этот слой отображает данные из Data Layer и реагирует на сигналы из Logic Layer, но не содержит бизнес-логики. HUD обновляет полоску здоровья, когда получает сигнал health_changed, но не вычисляет урон самостоятельно.

**Persistence Layer (Слой хранения):** SaveManager (Autoload) — сериализует состояние игры в JSON, десериализует при загрузке. Каждый менеджер предоставляет методы get_save_data() и load_save_data(), а SaveManager координирует процесс, собирая данные от всех менеджеров в единую структуру. InventorySystem.to_dict() конвертирует C++ структуры в Dictionary для совместимости с Godot.

## 2.5 Паттерны проектирования

Проект использует следующие паттерны, каждый из которых решает конкретную задачу:

### Конечный автомат (FSM) — NPCController

NPCController использует FSM для управления поведением NPC. Каждое состояние (Idle, Patrol, Follow, Flee, Attack, Stunned) реализует методы `enter()`, `update()` и `exit()`. Переходы управляются условиями: расстояние до игрока, уровень здоровья, наличие линии видимости. Реализация в C++ обеспечивает быстрое переключение для 10–20 NPC одновременно без падения FPS.

```
Idle ──(игрок в detect_range)──▶ Follow ──(игрок в attack_range)──▶ Attack
 ▲                                  │                                  │
 │                                  │(HP < 20%)                        │(игрок ушёл)
 │                                  ▼                                  │
 │                              Flee ◀───────────────────────────────┘
 │                                  │
 │  (игрок вышел из detect_range)   │(достиг точки бегства)
 │                                  ▼
 └──────────────────────────── Idle/Patrol
```

### Strategy — CombatController для комбо

CombatController использует паттерн Strategy для комбо-цепочек. Разные оружия определяют разные последовательности ударов: меч — 3 лёгких + 1 тяжёлый, лук — быстрые выстрелы. Стратегия комбо определяется экипированным оружием и может быть заменена без изменения CombatController.

### Observer — QuestSystem и диалоги

QuestSystem реализует паттерн Observer: диалоговые триггеры подписаны на сигнал `quest_state_changed`, NPC обновляют доступные реплики при изменении состояния квеста. Это слабосвязанная архитектура: квестовая система не знает о конкретных NPC, а NPC не знают о внутренней логике квестов.

### Data-View — ресурсы и UI

Все данные определены как Resource (Data), а UI (View) подписан на сигналы об их изменении. InventoryPanel обновляется при сигнале `inventory_changed`, но не знает, откуда пришли предметы. DialoguePanel отображает DialogueData, но не проверяет условия — это делает C++ код.

### Factory — создание предметов и врагов

Предметы создаются фабричным методом: `ItemFactory.create_item(item_id)` загружает соответствующую сцену из ItemData.world_scene и настраивает параметры. Враги создаются `EnemySpawner.spawn(enemy_data)` на основе EnemyData. Фабрика изолирует создание объектов от бизнес-логики.

Все данные определены как GDScript Resources с @export переменными. Это позволяет настраивать параметры в инспекторе Godot без изменения кода. C++ классы читают эти ресурсы через GDExtension API.

```cpp
void AdventureCharacter::_physics_process(double delta) {
    // Гравитация с переменной высотой прыжка
    if (!is_on_floor()) {
        double grav = velocity.y < 0.0 ? fall_gravity : jump_gravity;
        velocity.y -= grav * delta;

        // Укороченный прыжок при отпускании кнопки
        if (velocity.y > 0.0 && !Input::get_singleton()->is_action_pressed("jump")) {
            velocity.y *= 0.5;
        }
    } else if (Input::get_singleton()->is_action_just_pressed("jump")) {
        velocity.y = jump_velocity;
    }

    // Движение относительно камеры
    Vector3 input_dir = _get_camera_relative_input();
    bool sprinting = Input::get_singleton()->is_action_pressed("sprint");
    double current_speed = sprinting ? sprint_speed : move_speed;

    velocity.x = input_dir.x * current_speed;
    velocity.z = input_dir.z * current_speed;

    set_velocity(velocity);
    move_and_slide();

    // Поворот персонажа к направлению движения
    if (input_dir.length_squared() > 0.01) {
        Vector3 target_direction = -input_dir;
        double target_yaw = Math::atan2(target_direction.x, target_direction.z);
        Quaternion target_quat = Quaternion(Vector3(0, 1, 0), target_yaw);
        Quaternion current_quat = get_global_transform().basis.get_rotation_quaternion();
        Quaternion new_quat = current_quat.slerp(target_quat, rotation_speed * delta);
        set_global_transform(Transform3D(Basis(new_quat), get_global_position()));
    }
}

Vector3 AdventureCharacter::_get_camera_relative_input() const {
    auto *input = Input::get_singleton();
    Vector2 raw = input->get_vector("move_left", "move_right", "move_forward", "move_back");

    if (!camera_pivot) {
        return Vector3(raw.x, 0.0, raw.y).normalized();
    }

    Vector3 cam_forward = -camera_pivot->get_global_basis().get_column(2);
    Vector3 cam_right = camera_pivot->get_global_basis().get_column(0);

    cam_forward.y = 0.0;
    cam_forward.normalize();
    cam_right.y = 0.0;
    cam_right.normalize();

    return (cam_forward * raw.y + cam_right * raw.x).normalized();
}
```

```cpp

#include <godot_cpp/classes/input.hpp>
#include <godot_cpp/variant/math.hpp>

namespace adv {

void CameraController::_process(double delta) {
    switch (current_mode) {
        case CameraMode::FOLLOW:    _update_follow(delta); break;
        case CameraMode::CINEMATIC: _update_cinematic(delta); break;
        case CameraMode::FIXED:     break; // Статичная камера
        case CameraMode::TRANSITION: _update_transition(delta); break;
    }
}

void CameraController::_update_follow(double delta) {
    auto *input = Input::get_singleton();

    // Вращение камеры
    Vector2 cam_input = input->get_vector("camera_left", "camera_right", "camera_up", "camera_down");
    yaw += cam_input.x * rotation_speed * delta;
    pitch = Math::clamp(pitch + cam_input.y * rotation_speed * delta, min_pitch, max_pitch);

    // Применяем вращение к SpringArm3D (дочерний узел)
    set_rotation(Vector3(Math::deg_to_rad(pitch), Math::deg_to_rad(yaw), 0.0));

    // Плавное следование за персонажем
    if (follow_target) {
        Vector3 target = follow_target->get_global_position();
        Vector3 current = get_global_position();
        double factor = 1.0 - Math::exp(-smooth_speed * delta);
        set_global_position(current.lerp(target, factor));
    }
}

void CameraController::_update_transition(double delta) {
    transition_progress += delta / transition_duration;
    if (transition_progress >= 1.0) {
        transition_progress = 1.0;
        set_global_transform(transition_to);
        current_mode = CameraMode::CINEMATIC;
        return;
    }
    // Smoothstep интерполяция
    double t = transition_progress * transition_progress * (3.0 - 2.0 * transition_progress);
    Vector3 pos = transition_from.origin.lerp(transition_to.origin, t);
    Quaternion rot = transition_from.basis.get_rotation_quaternion().slerp(
        transition_to.basis.get_rotation_quaternion(), t);
    set_global_transform(Transform3D(Basis(rot), pos));
}

void CameraController::set_mode(CameraMode mode) {
    if (current_mode == mode) return;
    current_mode = mode;
}

void CameraController::transition_to(const Transform3D &target, double duration) {
    transition_from = get_global_transform();
    transition_to = target;
    transition_progress = 0.0;
    transition_duration = Math::max(0.1, duration);
    current_mode = CameraMode::TRANSITION;
}

} // namespace adv
```

```cpp
    // Получаем ссылку на игрока через группу

    if (!nav_agent || !player_ref) return;

    switch (current_state) {
        case NPCState::IDLE:     _update_idle(delta); break;
        case NPCState::PATROL:   _update_patrol(delta); break;
        case NPCState::FOLLOW:   _update_follow(delta); break;
        case NPCState::ATTACK:   _update_attack(delta); break;
        case NPCState::FLEE:     _update_flee(delta); break;
        case NPCState::STUNNED:  _update_stunned(delta); break;
        case NPCState::DEAD:     break;
    }

    // Навигация
    if (current_state != NPCState::IDLE && current_state != NPCState::STUNNED
        && current_state != NPCState::DEAD) {
        Vector3 next_pos = nav_agent->get_next_path_position();
        Vector3 direction = (next_pos - get_global_position()).normalized();
        Vector3 vel = direction * move_speed;
        vel.y = get_velocity().y;

        set_velocity(vel);
        move_and_slide();
    }
}

    if (idle_timer >= idle_wait_time) {
        idle_timer = 0.0;
        _transition_to(NPCState::PATROL);
    }

    // Обнаружение игрока
    if (player_ref) {
        double dist = get_global_position().distance_to(player_ref->get_global_position());
        if (dist <= detect_range) {
            _transition_to(NPCState::FOLLOW);
        }
    }
}

        _transition_to(NPCState::IDLE);
        return;

    Vector3 target = patrol_points[current_patrol_index];
    nav_agent->set_target_position(target);

    if (get_global_position().distance_to(target) < 1.0) {
        current_patrol_index = (current_patrol_index + 1) % patrol_points.size();
    }

    // Обнаружение игрока
    if (player_ref) {
        double dist = get_global_position().distance_to(player_ref->get_global_position());
        if (dist <= detect_range) {
            _transition_to(NPCState::FOLLOW);
        }
    }
```

```cpp
#include "inventory_system.h"
#include <godot_cpp/variant/utility_functions.hpp>

namespace adv {

bool InventorySystem::add_item(const StringName &item_id, int count) {
    if (count <= 0) return false;

    // Проверяем, есть ли уже такой предмет
    auto it = item_counts.find(item_id);
    if (it != item_counts.end()) {
        it->second += count;
        _emit_inventory_changed();
        return true;
    }

    // Ищем пустой слот
    for (auto &slot : slots) {
        if (slot.count == 0) {
            slot.item_id = item_id;
            slot.count = count;
            item_counts[item_id] = count;
            _emit_inventory_changed();
            return true;
        }
    }

    // Нет пустых слотов
    return false;
}

bool InventorySystem::remove_item(const StringName &item_id, int count) {
    auto it = item_counts.find(item_id);
    if (it == item_counts.end() || it->second < count) return false;

    it->second -= count;
    if (it->second <= 0) {
        item_counts.erase(it);
        // Очищаем слот
        for (auto &slot : slots) {
            if (slot.item_id == item_id) {
                slot.item_id = StringName();
                slot.count = 0;
                break;
            }
        }
    }

    _emit_inventory_changed();
    return true;
}

bool InventorySystem::has_item(const StringName &item_id, int count) const {
    auto it = item_counts.find(item_id);
    return it != item_counts.end() && it->second >= count;
}

int InventorySystem::get_count(const StringName &item_id) const {
    auto it = item_counts.find(item_id);
    return it != item_counts.end() ? it->second : 0;
}

Dictionary InventorySystem::to_dict() const {
    Dictionary result;
    for (const auto &slot : slots) {
        if (slot.count > 0) {
            result[slot.item_id] = slot.count;
        }
    }
    return result;
}

void InventorySystem::from_dict(const Dictionary &data) {
    item_counts.clear();
    for (auto &slot : slots) {
        slot = ItemSlot();
    }

    const Array keys = data.keys();
    int slot_idx = 0;
    for (int i = 0; i < keys.size() && slot_idx < max_slots; ++i) {
        StringName key = keys[i];
        int count = data[key];
        slots[slot_idx].item_id = key;
        slots[slot_idx].count = count;
        item_counts[key] = count;
        slot_idx++;
    }

    _emit_inventory_changed();
}

    emit_signal("inventory_changed");
}

    slots.resize(max_slots);
```

```gdscript

    if current_line_index >= current_dialogue.lines.size():
        _close_dialogue()
        return

    var line: DialogueLine = current_dialogue.lines[current_line_index]

    # Проверка условия (делегируется C++ через QuestSystem)
    if line.condition != "" and not _check_condition(line.condition):
        current_line_index += 1
        _show_line()
        return

    speaker_label.text = line.speaker
    text_label.text = line.text
    _update_choices(line.choices)

func _update_choices(choices: Array[DialogueChoice]) -> void:
    # Очищаем старые кнопки
    for child in choices_container.get_children():
        child.queue_free()

    if choices.is_empty():
        # Нет выбора — показываем "Продолжить"
        var btn := Button.new()
        btn.text = "Продолжить"
        btn.pressed.connect(_on_continue)
        choices_container.add_child(btn)
        return

    for i in range(choices.size()):
        var choice: DialogueChoice = choices[i]
        if choice.condition != "" and not _check_condition(choice.condition):
            continue
        var btn := Button.new()
        btn.text = choice.text
        var idx := i
        btn.pressed.connect(func(): _on_choice_selected(idx, choice))
        choices_container.add_child(btn)

func _on_continue() -> void:
    var line: DialogueLine = current_dialogue.lines[current_line_index]
    if line.on_complete != "":
        _execute_action(line.on_complete)
    current_line_index += 1
    _show_line()

    choice_made.emit(index)
    if choice.on_select != "":
        _execute_action(choice.on_select)
    if choice.next_line_index >= 0:
        current_line_index = choice.next_line_index
    else:
        _close_dialogue()
        return

    panel.visible = false
    dialogue_finished.emit()

    # Делегируем проверку условий C++ QuestSystem
    # Формат: "has_item:forest_key", "quest_state:forest_clear:completed"
    var parts := condition.split(":")
    if parts.size() < 2:
        return true
    match parts[0]:
        "has_item":
            return _get_inventory().has_item(StringName(parts[1]))
        "quest_state":
            if parts.size() >= 3:
                return _get_quest_system().get_quest_state(StringName(parts[1])) == _str_to_state(parts[2])
        "has_gold":
            return _get_economy().has_gold(int(parts[1]))
    return true

    var parts := action.split(":")
    if parts.is_empty():
        return
    match parts[0]:
        "start_quest":
            if parts.size() >= 2:
                _get_quest_system().start_quest(StringName(parts[1]))
        "give_item":
            if parts.size() >= 3:
                _get_inventory().add_item(StringName(parts[1]), int(parts[2]))
        "give_gold":
            if parts.size() >= 2:
                _get_economy().add_gold(int(parts[1]))

    match s:
        "not_started": return 0
        "in_progress": return 1
        "completed": return 2
        "failed": return 3
    return -1
```

```gdscript
    if player:
        var health := player.get_node_or_null("HealthComponent")
        if health:
            save_data["health"] = health.get_save_data()
        var stamina := player.get_node_or_null("StaminaComponent")
        if stamina:
            save_data["stamina"] = stamina.get_save_data()
        save_data["player_position"] = {
            "x": player.global_position.x,
            "y": player.global_position.y,
            "z": player.global_position.z
        }

    # InventorySystem (C++) — через to_dict()
    var inventory := get_node_or_null("/root/InventorySystem")
    if inventory:
        save_data["inventory"] = inventory.to_dict()

    # QuestSystem (C++) — через to_dict()
    var quest_system := get_node_or_null("/root/QuestSystem")
    if quest_system:
        save_data["quests"] = quest_system.to_dict()

    var file := FileAccess.open(SAVE_PATH, FileAccess.WRITE)
    if not file:
        push_error("SaveManager: failed to open save file")
        return false
    file.store_string(JSON.stringify(save_data, "\t"))
    file.close()
    return true

func load_game() -> bool:
    if not FileAccess.file_exists(SAVE_PATH):
        return false

    var file := FileAccess.open(SAVE_PATH, FileAccess.READ)
    if not file:
        return false

    var json := JSON.new()
    var err := json.parse(file.get_as_text())
    file.close()
    if err != OK:
        push_error("SaveManager: failed to parse save file")
        return false

    var save_data: Dictionary = json.data

    # Восстанавливаем данные
    var economy := get_node_or_null("/root/EconomyManager")
    if economy and save_data.has("economy"):
        economy.load_save_data(save_data["economy"])

    var player := get_node_or_null("/root/GameManager").player
    if player and save_data.has("player_position"):
        var pos: Dictionary = save_data["player_position"]
        player.global_position = Vector3(pos.x, pos.y, pos.z)

    if player:
        var health := player.get_node_or_null("HealthComponent")
        if health and save_data.has("health"):
            health.load_save_data(save_data["health"])
        var stamina := player.get_node_or_null("StaminaComponent")
        if stamina and save_data.has("stamina"):
            stamina.load_save_data(save_data["stamina"])

    var inventory := get_node_or_null("/root/InventorySystem")
    if inventory and save_data.has("inventory"):
        inventory.from_dict(save_data["inventory"])

    var quest_system := get_node_or_null("/root/QuestSystem")
    if quest_system and save_data.has("quests"):
        quest_system.from_dict(save_data["quests"])

    return true

func has_save() -> bool:
    return FileAccess.file_exists(SAVE_PATH)

func delete_save() -> void:
    if has_save():
        DirAccess.remove_absolute(SAVE_PATH)
```

В следующем проекте (Проект 6: Performance Demo) мы добавим:

- ➕ **ECS-архитектура** — Entity-Component-System на C++ с Data Locality: компоненты хранятся в непрерывных массивах (SoA вместо AoS), итерация через view<Ts...> без виртуальных вызовов
- ➕ **Многопоточность** — Job-система (пул потоков) для параллельного обновления тысяч сущностей, std::atomic для потокобезопасных флагов
- ➕ **Compute-шейдеры** — GPU-симуляция boids и частиц через RenderingDevice, обмен данными CPU↔GPU через буферы
- ➕ **MultiMesh** — рендеринг 10 000 юнитов за 3 draw call (вместо 10 000 отдельных MeshInstance3D)
- ➕ **Кастомные аллокаторы** — PoolAllocator и ArenaAllocator для нулевых аллокаций в кадровом цикле
- ➕ **Frustum culling + LOD** — отсечение невидимых объектов и три уровня детализации (500/100/2 треугольника)

А также впервые встретимся с:

- ⚡ **Экстремальная оптимизация** — если Проект 4 показал, что C++ быстрее GDScript в 26 раз, то Проект 6 покажет, что правильно спроектированная архитектура данных (ECS + Data Locality) быстрее наивного C++ ещё в 20 раз. Вы увидите, как каждая техника добавляет свой вклад: MultiMesh даёт 7.5x, ECS — 2.7x, многопоточность — 2.3x, compute — 1.7x, frustum+LOD — 1.6x.
