## Обзор

Дорожная карта доработки контента курса на основе исследования существующих Godot-курсов. Основные цели: устранение Tutorial Hell, повышение глубины контента, добавление интерактивных элементов, уникальный GDScript → C++ переход.

### Что изменилось с версии 2.0

Версия 2.0 была выпущена сразу после завершения детализации всех 6 проектов и содержала много запланированных, но не реализованных задач. С тех пор произошли следующие изменения:

- **Блоки «Почему это работает именно так?»** — в проектах P2–P6 добавлены развёрнутые объяснения «под капотом» в контексте глав Архитектуры и Кода. Однако визуальные выноски (блоки-сноски) пока не внедрены — это задача конвертации в MDX.
- **course-overview.md** — ✅ обновлён до v2.0: устаревшие ссылки на docx заменены на md, добавлена трёхглавная структура, расширенная матрица навыков, методология «Анти-Tutorial Hell», паттерны проектирования по проектам.
- **Финальные спринты** — формат описан в v2.0, но не внедрён ни в один проект.
- **Мосты между проектами** — формат описан в v2.0, но формализованные мосты добавлены только в P1 (секция «Связь с проектом 2») и P2 (секция «Связь с проектом 3»). Остальные проекты содержат итоговые секции, но без формализованного формата мостов.
- **tech-debt.md** — актуализирован: контент уже в Markdown (не docx), что снимает TD-005 частично.
- **Шпаргалки, JSON-челленджи, starter-шаблоны, видео** — без изменений, не начаты.

Ключевой вывод: основа контента (13 156 строк в 6 проектных документах) полностью готова. Все проекты содержат главы Геймдизайна, Архитектуры и Кода с проверками. Теперь фокус смещается с «создания контента» на «доводку, структурирование и платформенную интеграцию».

### 1.1. Визуальные блоки «Почему это работает именно так?» ✦ ПЕРЕНОСИТСЯ В MDX

**Приоритет:** Средний (переносится на этап конвертации)  
**Охват:** Все 6 проектов

Объяснения «под капотом» уже встроены в текст каждого проекта (например, почему сигналы слабосвязанные в P1, почему Object Pool критичен для FPS в P2, почему ECS лучше OOP для кэша в P6). Добавлять визуальные Markdown-выноски сейчас — дублирование: при конвертации в MDX (Этап 3) эти фрагменты всё равно будут переработаны в `<Insight>` компоненты.

**Решение:** Вместо внедрения Markdown-выносок сейчас, создать список якорей (мест в тексте) для каждого проекта, которые при MDX-конвертации будут обёрнуты в `<Insight>` компоненты. Это сэкономит время и избежит двойной работы.

| Проект | Ключевые якоря для `<Insight>` | Примеры |
|---|---|---|
| P1 | Сигналы vs опрос, Autoload vs синглтон, _process vs Timer | «Почему сигналы слабосвязанные?» — §4.3 |
| P2 | Object Pool vs инстанцирование, Collision layers/masks | «Почему 1000 пуль без пуля убивают FPS?» — §5.4 |
| P3 | State Machine vs if/else, AnimationTree vs AnimationPlayer | «Зачем FSM если работают условия?» — §2.5 |
| P4 | C++ vs GDScript бенчмарки, A* vs NavigationServer | «Почему pathfinding на C++ в 26 раз быстрее?» — §2.5 |
| P5 | 3D камера с коллизиями, NavigationRegion3D bake | «Зачем SpringArm3D?» — Архитектура |
| P6 | ECS vs OOP для кэша, compute vs CPU, MultiMesh vs MeshInstance | «Почему SoA быстрее AoS?» — §1.5 |
