## 2.1 Обзор архитектуры (4 слоя)

Архитектура проекта строится на четырёх слоях, каждый из которых имеет чёткую зону ответственности. Такое разделение обеспечивает слабую связанность между системами и позволяет изменять один слой без каскадных изменений в остальных. Это особенно важно для метроидвании, где количество взаимозависимых систем значительно выше, чем в простых платформерах.

**Data Layer (Слой данных):** Содержит все данные, описывающие игровые объекты, но не содержащие логики. AbilityData, ItemData, EnemyData, RoomData — все наследуют Resource и используют @export для настройки в редакторе. Это позволяет геймдизайнеру настраивать параметры врагов, предметов и способностей без изменения кода, а программисту — ссылаться на типизированные данные вместо магических чисел.

**Logic Layer (Слой логики):** Содержит глобальные менеджеры, управляющие игровыми системами. GameManager (пауза, регистрация игрока), AbilityManager (разблокировка и проверка способностей), InventoryManager (добавление/удаление предметов), SceneManager (переходы между комнатами), SaveManager (сохранение/загрузка). Все менеджеры реализованы как Autoload (Singleton), что обеспечивает глобальный доступ без передачи ссылок через дерево сцен.

**Presentation Layer (Слой представления):** Содержит визуальные компоненты: Player, Enemy-сцены, HUD, InventoryUI, DamageNumber. Этот слой отображает данные из Data Layer и реагирует на сигналы из Logic Layer, но не содержит бизнес-логики. Например, HUD обновляет полоску здоровья, когда получает сигнал `health_changed`, но не вычисляет урон самостоятельно.

**Persistence Layer (Слой хранения):** Отвечает за сериализацию и десериализацию состояния игры. SaveManager единолично владеет структурой world_state и предоставляет методы для отметки убитых врагов, собранных предметов и открытых дверей. При сохранении все менеджеры отдают свои данные через метод `get_save_data()`, при загрузке — принимают через `load_save_data()`.

## 2.2 Дерево сцен

Дерево сцен — это визуальное представление архитектуры. Каждая сцена инкапсулирует свою функциональность и暴露ает только необходимые интерфейсы (сигналы, методы). Ниже приведены полные деревья для всех ключевых сцен проекта. Обратите внимание на то, как компоненты (Hitbox, Hurtbox, HealthComponent) используются повторно в разных сценах — это основа компонентного подхода.

### main.tscn

Главная сцена, которая загружается при старте игры. Она содержит менеджеры, игрока, HUD и слои переходов. SceneManager управляет динамической загрузкой комнат, а FadeOverlay обеспечивает визуально плавные переходы.

```
Main (Node2D) [scripts/main.gd]
├── SceneManager (Node) [autoload: scripts/scene_manager.gd]
│   ├── CurrentRoom (Node2D) — placeholder, динамически заменяемый
│   ├── Player (CharacterBody2D) [scenes/player.tscn]
│   └── FadeOverlay (ColorRect) — full screen, color: black, modulate.a: 0
├── HUD (CanvasLayer) [scenes/hud.tscn]
└── TransitionLayer (CanvasLayer)
    └── FadeOverlay (ColorRect) — full screen, color: black
```

### player.tscn

Все состояния FSM реализованы как дочерние узлы Node, что позволяет добавлять новые состояния без изменения существующего кода.

Шаблон комнаты, от которого наследуются все комнаты в игре. ## 2.3 Диаграмма классов

## 2.4 Поток данных

Понимание потока данных — ключ к отладке и расширению проекта. Ниже описаны два ключевых сценария с пошаговым прослеживанием сигналов и вызовов методов. Каждый шаг помечен источником (кто инициирует) и типом взаимодействия (сигнал, прямой вызов, проверка свойства).

### Сценарий 1: Игрок получает урон от врага

1. **Физический движок** обнаруживает пересечение Area2D: Hitbox врага входит в Hurtbox игрока
2. **Hurtbox игрока** (`_on_area_entered`) проверяет, что входящая область в группе `"hitbox"` и не принадлежит самому игроку
3. **Hurtbox игрока** извлекает `damage` из Hitbox врага и вызывает `player.take_damage(damage, hitbox.global_position)`
4. **Player.take_damage()** проверяет `invincible` и `is_hurt`; если оба false — уменьшает `health`, что вызывает setter, который эмитит `health_changed`
5. **Player.take_damage()** вызывает `apply_knockback(source_pos, 250.0)`, устанавливая `velocity` в направлении от источника
6. **Player.take_damage()** вызывает переход в состояние Hurt через `state_machine._on_transition_requested(&"Hurt")`
7. **HurtState.enter()** устанавливает `is_hurt = true` и вызывает `player.start_invincibility(1.0)`
8. **Player.start_invincibility()** устанавливает `invincible = true` и запускает Tween для мигания спрайта
9. **HUD** получает сигнал `health_changed` и обновляет полоску здоровья
10. **HurtState.physics_update()** уменьшает таймер; по истечении — переход в Idle/Run/Fall/Dead
11. **Tween** завершается и сбрасывает `invincible = false`

### Сценарий 2: Игрок подбирает способность (ability pickup)

1. **Физический движок** обнаруживает: тело игрока входит в Area2D способности
2. **AbilityPickup._on_body_entered()** проверяет, что body в группе `"player"` и способность ещё не разблокирована
3. **AbilityPickup** вызывает `AbilityManager.unlock_ability(ability_id)`
4. **AbilityManager.unlock_ability()** добавляет `ability_id` в словарь `_abilities` и эмитит сигнал `ability_unlocked(ability_id)`
5. **AbilityPickup** вызывает `SaveManager.mark_item_collected(room_id, pickup_id)` для сохранения факта подбора
6. **AbilityPickup** воспроизводит звук через `AudioManager.play_sfx("ability_unlock")` и уничтожается (`queue_free()`)
7. **HUD** получает сигнал `ability_unlocked` и добавляет индикатор способности в AbilityIndicator
8. **Player** (в состояниях Jump, Dash, WallSlide) теперь получает доступ к новой способности через `AbilityManager.has_ability()`
9. **RoomTransition** с `required_ability = ability_id` теперь пропускает игрока, открывая новую область
10. При следующем сохранении `SaveManager.save_game()` сохраняет `_abilities` через `AbilityManager.get_save_data()`

## 2.5 Паттерны проектирования

Проект использует семь ключевых паттернов проектирования, каждый из которых решает конкретную проблему. Понимание этих паттернов и причин их применения критически важно для расширения проекта и избежания типичных ошибок.

| Паттерн | Где применён | Зачем |
|---|---|---|
| Observer (Сигналы) | `ability_unlocked`, `health_changed`, `room_changed`, `inventory_changed`, `player_died` | Слабая связанность между системами: HUD обновляется автоматически при изменении здоровья, без прямых вызовов из Player |
| State Machine | Player FSM (9 состояний), Enemy FSM (5 состояний) | Управление сложным поведением: каждый state инкапсулирует свою логику, переходы чётко определены, невозможно оказаться в «промежуточном» состоянии |
| Strategy | AbilityManager + match в состояниях игрока | Разные способности обрабатываются единообразно: проверка `has_ability()` в состоянии решает, доступно ли действие, без if-else цепочек |
| Singleton (Autoload) | GameManager, SaveManager, SceneManager, AbilityManager, InventoryManager, AudioManager | Глобальный доступ к менеджерам без передачи ссылок через дерево сцен; Godot Autoload гарантирует единственный экземпляр |
| Factory | `PackedScene.instantiate()` для снарядов, чисел урона, предметов | Динамическое создание объектов в рантайме: снаряды создаются при стрельбе, числа урона — при попадании |
| Data-View separation | ItemData/AbilityData (Resource) vs UI-сцены | Данные отделены от отображения: геймдизайнер настраивает ItemData в инспекторе, UI автоматически подстраивается |
| Component | HealthComponent, Hitbox, Hurtbox — переиспользуемые узлы | Композиция вместо наследования: враги и игрок используют одни и те же компоненты, что упрощает добавление новых типов врагов |
