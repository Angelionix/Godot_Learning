Хорошая архитектура — это не роскошь, а необходимость. Даже в небольшом проекте, как наш кликер, смешивание данных, логики и отображения в одном скрипте быстро приводит к «спагетти-коду», который невозможно ни понять, ни изменить. В этой главе мы определим чёткую слоистую архитектуру, где каждый компонент имеет единственную ответственность. Этот подход не просто делает код чище — он делает его проверяемым, расширяемым и понятным для других разработчиков.

## 2.1 Обзор архитектуры

Наш проект разделён на четыре логических слоя, каждый из которых выполняет строго определённую роль:

**Data Layer (Слой данных):** Классы `UpgradeData` и `AchievementData`, расширяющие `Resource`. Это чистые данные — они не содержат игровой логики, только структуру и базовые вычисления (например, стоимость апгрейда на текущем уровне). Resource выбран как базовый класс, потому что он поддерживает экспорт в Inspector, сериализацию и сохранение как .tres-файлы.

**Logic Layer (Слой логики):** `GameManager` (Autoload) — центральный контроллер игрового состояния. Он знает правила игры: как добавляется валюта, как применяются апгрейды, как проверяются достижения. GameManager ничего не знает об интерфейсе — он лишь уведомляет об изменениях через сигналы.

**Presentation Layer (Слой отображения):** Сцены `Main`, `UpgradeItem`, `FloatingText` — всё, что видит игрок. Эти компоненты подписываются на сигналы GameManager и обновляют UI соответственно. Ни один визуальный компонент не содержит бизнес-логики.

**Persistence Layer (Слой сохранения):** `SaveManager` (Autoload) — отвечает исключительно за сериализацию и десериализацию данных. Он не знает, что именно он сохраняет — он просто берёт Dictionary от GameManager и записывает его в файл, а при загрузке — читает файл и передаёт Dictionary обратно.

Почему это разделение критически важно для курса: студенты, которые впервые пишут игру, часто помещают всю логику в скрипт главной сцены. Результат — монолитный файл на 500 строк, где обработка клика, расчёт стоимости, обновление UI и сохранение перемешаны. Когда нужно добавить новую фичу, приходится искать нужное место среди сотен строк не связанного кода. Разделение по слоям гарантирует, что изменение визуальных эффектов не сломает экономику, а добавление нового типа апгрейда не потребует изменений в UI.

Обратите внимание на использование CanvasLayer для UILayer и EffectsLayer. CanvasLayer создаёт независимый слой отрисовки с собственным порядком рендеринга. Это гарантирует, что UI-элементы всегда отображаются поверх игрового мира, а визуальные эффекты — поверх UI. EffectsLayer имеет более высокий layer-индекс, чем UILayer, чтобы всплывающие числа и конфетти отрисовывались поверх кнопок и лейблов.

## 2.3 Диаграмма классов

Диаграмма ниже показывает отношения между основными классами проекта. Стрелки обозначают направление зависимости: если A указывает на B, значит A знает о B, но B не знает об A. Обратите внимание, что визуальные компоненты (Main, UpgradeItem) зависят от GameManager, но GameManager ничего не знает о них — он лишь испускает сигналы.

```
┌─────────────────────────────────────────────────────┐
│                    GameManager                       │
│                  (Autoload/Node)                     │
├─────────────────────────────────────────────────────┤
│ - currency: int                                      │
│ - click_power: int                                   │
│ - auto_click_power: int                              │
│ - total_clicks: int                                  │
│ - total_currency_earned: int                         │
│ - upgrades: Dictionary[String, UpgradeData]          │
│ - achievements: Array[AchievementData]               │
├─────────────────────────────────────────────────────┤
│ + add_currency(amount: int) -> void                  │
│ + purchase_upgrade(id: String) -> bool               │
│ + apply_upgrade_effect(upgrade: UpgradeData) -> void │
│ + check_achievements() -> void                       │
│ + save_game() -> bool                                │
│ + load_game() -> bool                                │
│ + calculate_offline_progress() -> void               │
│ + reset_game() -> void                               │
├─────────────────────────────────────────────────────┤
│ signal currency_changed(new_amount: int)             │
│ signal stats_updated()                               │
│ signal achievement_unlocked(achievement: Achievement) │
│ signal upgrade_purchased(upgrade: UpgradeData)       │
└─────────────────┬───────────────────────────────────┘
                  │ uses
    ┌─────────────┼──────────────┐
    ▼             ▼              ▼
┌──────────┐ ┌──────────┐ ┌───────────────┐
│UpgradeData│ │Achievement│ │ (SaveManager) │
│(Resource)│ │  Data     │ │  (Autoload)   │
└──────────┘ │(Resource) │ └───────────────┘
             └──────────┘
```

Ключевой принцип: GameManager — единственный источник истины (single source of truth) для игрового состояния. Все другие компоненты читают данные из GameManager или подписываются на его сигналы. Если бы мы позволили UpgradeItem напрямую изменять валюту, мы бы нарушили этот принцип и создали бы расхождение данных.

## 2.4 Поток данных

Понимание потока данных — ключ к пониманию архитектуры. Давайте проследим два основных сценария:

**Сценарий 1: Игрок кликает по кнопке**

```
Игрок кликает
    ↓
Main._on_click_button_pressed()
    ↓
GameManager.on_click()
    ├── total_clicks += 1
    ├── add_currency(click_power)
    │   ├── currency += click_power
    │   ├── total_currency_earned += click_power
    │   ├── currency_changed.emit(currency) ───→ Main._on_currency_changed() → обновляет лейбл
    │   ├── stats_updated.emit() ───→ Main._on_stats_updated() → обновляет статистику
    │   └── check_achievements() → проверяет условия, если открыто — achievement_unlocked.emit()
    ↓
Main.spawn_floating_text() → создаёт FloatingText на EffectsLayer
Main.animate_button() → scale down, плавный возврат через _process()
```

**Сценарий 2: Игрок покупает апгрейд**

```
Игрок нажимает "Купить"
    ↓
UpgradeItem._on_buy_pressed()
    ↓ purchase_callback.call(data)
Main._on_upgrade_buy_requested(upgrade)
    ↓
GameManager.purchase_upgrade(id)
    ├── Проверяет: существует ли апгрейд? Достаточно ли валюты?
    ├── currency -= cost
    ├── upgrade.purchase() → level += 1
    ├── apply_upgrade_effect(upgrade) → изменяет click_power / auto_click_power
    ├── upgrade_purchased.emit(upgrade) ───→ Main._on_upgrade_purchased() → обновляет магазин
    ├── currency_changed.emit(currency) ───→ Main обновляет лейбл + доступность кнопок
    ├── stats_updated.emit() ───→ Main обновляет статистику
    ├── check_achievements()
    ↓
Main вызывает SaveManager.save_game()
```

Обратите внимание: каждый сигнал может иметь несколько подписчиков, но испускатель сигнала не знает, кто именно на него подписан. Это и есть слабая связанность — ядро нашей архитектуры. Если в будущем мы добавим звуковой менеджер, он просто подпишется на `currency_changed` и `upgrade_purchased`, не требуя изменений в GameManager.

## 2.5 Паттерны проектирования

Осознанное применение паттернов проектирования отличает профессиональный код от любительского. В нашем проекте используются шесть паттернов, каждый из которых решает конкретную проблему:

| Паттерн | Где применён | Зачем |
|---|---|---|
| Observer (Сигналы) | currency_changed, stats_updated, upgrade_purchased, achievement_unlocked | Слабая связанность: UI не знает о GameManager напрямую, а GameManager не знает об UI. Компоненты общаются только через сигналы. |
| Strategy | UpgradeType enum + match в apply_upgrade_effect() | Разные эффекты апгрейдов обрабатываются единообразно без дублирования кода. Добавление нового типа — новая ветка в match. |
| Delegation (Callable) | UpgradeItem.purchase_callback | Компонент UpgradeItem не зависит от GameManager — он получает функцию обратного вызова извне. Это делает его переиспользуемым. |
| Singleton (Autoload) | GameManager, SaveManager | Глобальный доступ к центральным подсистемам. Autoload гарантирует, что экземпляр существует ровно один. |
| Factory | PackedScene.instantiate() | Динамическое создание FloatingText и частиц. PackedScene выступает фабрикой, создающей экземпляры по требованию. |
| Data-View separation | UpgradeData (Resource) vs UpgradeItem (Control) | Данные отделены от отображения. UpgradeData можно тестировать без UI, а UpgradeItem можно переиспользовать с другими данными. |

Каждый из этих паттернов не является искусственным усложнением — он решает реальную проблему, с которой вы столкнётесь при разработке. Без Observer пришлось бы передавать ссылки на все UI-элементы в GameManager. Без Delegation UpgradeItem был бы жёстко привязан к GameManager. Без Data-View separation изменение визуального стиля потребовало бы переписывания бизнес-логики.

## 2.6 Структура файлов проекта

Правильная организация файлов — это не вопрос эстетики, а вопрос продуктивности. В проекте с десятью файлами можно найти что угодно. В проекте с сотней — уже нет. Начните с правильной структуры с первого дня.

```
res://
├── scenes/
│   ├── main.tscn
│   ├── upgrade_item.tscn
│   ├── floating_text.tscn
│   └── confetti_particles.tscn
├── scripts/
│   ├── main.gd
│   ├── game_manager.gd
│   ├── save_manager.gd
│   ├── upgrade_data.gd
│   ├── upgrade_item.gd
│   ├── achievement_data.gd
│   └── floating_text.gd
├── resources/
│   └── upgrades_config.tres   (опционально: Resource с конфигурацией)
├── assets/
│   ├── images/
│   │   ├── coin_button_normal.png
│   │   ├── coin_button_pressed.png
│   │   └── coin_button_hover.png
│   ├── fonts/
│   │   └── game_font.tres
│   └── audio/
│       ├── click_sound.wav
│       ├── purchase_sound.wav
│       └── achievement_sound.wav
├── data/                       (создаётся автоматически при сохранении)
└── project.godot
```

Директория `data/` создаётся автоматически при первом сохранении — не создавайте её вручную. Директория `resources/` опциональна: в нашей реализации мы создаём апгрейды программно в GameManager, но альтернативный подход — определить их как .tres-файлы и загружать через ResourceLoader. Второй подход удобнее для нетехнических дизайнеров, которые могут настраивать баланс через Inspector, не трогая код.
