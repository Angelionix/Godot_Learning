## 2.1 Обзор архитектуры (4 слоя)

Проект следует 4-слойной архитектуре, которая чётко разделяет данные, логику, представление и персистентность. Каждый слой взаимодействует только с соседними, что обеспечивает модульность и тестируемость. В отличие от предыдущих проектов, где все слои были реализованы на GDScript, здесь слои Data и Logic полностью реализованы на C++, а Presentation использует гибридный подход (C++ для MultiMesh, GDScript для HUD).

```
┌─────────────────────────────────────────────────────────┐
│                    PRESENTATION LAYER                     │
│        MultiMeshInstance3D, GPUParticles3D, Camera3D     │
│              HUD (GDScript), PerfMonitor (C++)           │
├─────────────────────────────────────────────────────────┤
│                      LOGIC LAYER                         │
│     ECS Systems (C++), Job System, Compute Shaders       │
│     Frustum Culling, LOD, Boids AI, Collision            │
├─────────────────────────────────────────────────────────┤
│                       DATA LAYER                         │
│     ECS Registry (C++), Components, Archetypes           │
│     Pool Allocator, Arena Allocator, Spatial Hash        │
├─────────────────────────────────────────────────────────┤
│                   PERSISTENCE LAYER                      │
│     Config Resources (GDScript), Scene Settings          │
└─────────────────────────────────────────────────────────┘
```

### Граница C++ / GDScript

Критически важное решение — где провести границу между C++ и GDScript. Принцип прост: C++ для горячего кода (выполняется каждый кадр для тысяч сущностей), GDScript для холодного кода (настройка, UI, координация).

| Слой | Язык | Причина |
| --- | --- | --- |
| Data Layer (ECS Registry, Components) | C++ | Тысячи обращений за кадр, нужна Data Locality |
| Logic Layer (Systems, Job System) | C++ | Горячий цикл, многопоточность, compute |
| Presentation (MultiMesh обновление) | C++ | Обновление 10K трансформ каждый кадр |
| Presentation (HUD, PerfMonitor display) | GDScript | Низкая частота обновления, удобство |
| Persistence (Config Resources) | GDScript + Resource | Настройка через инспектор, не в горячем цикле |
| ECSWorld (координация) | C++ с GDScript bindings | Владеет Registry, вызывает Systems, экспортирует параметры |

### Поток данных через слои

```
GDScript Inspector → ECSWorld._ready() → Registry.emplace() [Data Layer]
                                        → Systems.init() [Logic Layer]
                                        
Each Frame:
  ECSWorld._process(delta) → JobSystem.submit_batch() [Logic Layer]
                           → MovementSystem.update() [Logic Layer]
                           → BoidSystem.update() [Logic/Compute Layer]
                           → RenderSystem.update() [Logic → Presentation]
                           → FrustumCulling.update() [Logic Layer]
                           → LODSystem.update() [Logic Layer]
                           → PerfMonitor.update() [Presentation Layer]
```

### Описание ключевых узлов

**ECSWorld** — единственный C++ узел, который владеет всем ECS-миром. Он не имеет визуального представления, но экспортирует параметры в инспектор Godot через `GDCLASS` и `PropertyList`. Через инспектор можно настроить: количество юнитов каждого типа, скорость симуляции, радиус поля битвы, включение/выключение отдельных Systems.

**InfantryMesh / CavalryMesh / ArcherMesh** — три MultiMeshInstance3D, каждый рендерит один тип юнитов за один draw call. ECSWorld получает указатели на эти MultiMesh через `get_node()` и передаёт их в RenderSystem для обновления трансформ каждый кадр.

**PerfMonitor** — C++ узел, который собирает метрики из ECSWorld и отображает их в HUD. Он вычисляет FPS, Frame Time, Draw Calls и обновляет HUD-элементы (созданные в GDScript или через CanvasItem) каждый кадр.

## 2.4 Поток данных

Поток данных в демо чётко разделён на фазы, каждая из которых выполняется последовательно в `_process()`. Это гарантирует, что системы, зависящие от результатов предыдущих систем, получают актуальные данные.

```
┌─────────────────────────────────────────────────────────────────┐
│                     FRAME PIPELINE                               │
│                                                                  │
│  1. INPUT                                                        │
│     Camera input → Camera position update                       │
│     Parameter changes → ECSWorld configuration                  │
│                                                                  │
│  2. PHYSICS / MOVEMENT  (фоновые потоки через JobSystem)        │
│     ┌──────────────────────────────────────────────┐            │
│     │ MovementSystem.update(delta)                  │            │
│     │   pos += vel × delta  (для всех Transform+Vel)│            │
│     │   [parallel: JobSystem.submit_batch]          │            │
│     └──────────────────────────────────────────────┘            │
│                                                                  │
│  3. AI / BOIDS  (compute-шейдер или CPU fallback)               │
│     ┌──────────────────────────────────────────────┐            │
│     │ BoidSystem.update(delta)                      │            │
│     │   SpatialHash.rebuild(positions)              │            │
│     │   Для каждого boid:                           │            │
│     │     neighbors = spatial_hash.query(pos)       │            │
│     │     steer = separation + alignment + cohesion │            │
│     │     velocity += steer × delta                 │            │
│     └──────────────────────────────────────────────┘            │
│                                                                  │
│  4. COMBAT  (фоновые потоки)                                    │
│     ┌──────────────────────────────────────────────┐            │
│     │ CombatSystem.update(delta)                    │            │
│     │   Проверка столкновений по SpatialHash        │            │
│     │   Нанесение урона по HealthComponent          │            │
│     └──────────────────────────────────────────────┘            │
│                                                                  │
│  5. CULLING + LOD  (главный поток, нужен Camera3D)              │
│     ┌──────────────────────────────────────────────┐            │
│     │ FrustumCulling.update(camera)                 │            │
│     │   Извлечь 6 плоскостей frustum               │            │
│     │   Пометить невидимые Renderable.visible=false │            │
│     │ LODSystem.update(camera_pos)                  │            │
│     │   Рассчитать дистанцию для каждого юнита      │            │
│     │   Обновить mesh_index в RenderableComponent   │            │
│     └──────────────────────────────────────────────┘            │
│                                                                  │
│  6. RENDER SYNC  (главный поток, доступ к Godot API)            │
│     ┌──────────────────────────────────────────────┐            │
│     │ RenderSystem.update(registry)                 │            │
│     │   Для каждого Transform + Renderable:         │            │
│     │     multimesh->set_instance_transform(i, t)   │            │
│     │   multimesh->set_visible_instance_count(cnt)  │            │
│     └──────────────────────────────────────────────┘            │
│                                                                  │
│  7. MONITORING  (главный поток)                                 │
│     PerfMonitor.update() → FPS, FrameTime, DrawCalls            │
│                                                                  │
│  8. GPU PARTICLES  (асинхронно, на GPU)                         │
│     GPUParticles3D update (выполняется Godot автоматически)     │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Временная диаграмма (параллельное выполнение)

```
Главный поток:    [Input] [Job submit] [wait] [Culling] [RenderSync] [Monitor]
                          ↓               ↑
Поток 1:                  [Movement 0-1250] [Boid 0-1250]
Поток 2:                  [Movement 1250-2500] [Boid 1250-2500]
Поток 3:                  [Movement 2500-3750] [Boid 2500-3750]
Поток 4:                  [Movement 3750-5000] [Boid 3750-5000]
...
Поток 7:                  [Movement 8750-10000] [Boid 8750-10000]

GPU:              [Compute Boids] [Compute Particles] [Render MultiMesh]
```

Movement и Boid фазы выполняются параллельно на 8 потоках. После `wait_all()` главный поток выполняет Culling и RenderSync, которым нужен доступ к Godot API. GPU работает параллельно с CPU: compute-шейдеры запускаются в начале кадра, а рендеринг MultiMesh происходит в конце.

## 2.5 Паттерны проектирования

### Паттерн: Entity-Component-System (ECS)

ECS — это основной архитектурный паттерн проекта. В отличие от OOP, где объект объединяет данные и логику, ECS разделяет их: Entity — это просто ID, Component — данные без логики, System — логика без данных. Это обеспечивает максимальную Data Locality и простую параллелизацию.

```
OOP подход (плохо для кэша):
  Unit { position, velocity, health, mesh, ai_state, ... }
  ↑ каждый Unit разбросан в куче, кэш-промахи при обходе

ECS подход (хорошо для кэша):
  Position[] = [p0, p1, p2, ..., p9999]  ← непрерывный массив
  Velocity[] = [v0, v1, v2, ..., v9999]  ← непрерывный массив
  Health[]   = [h0, h1, h2, ..., h9999]  ← непрерывный массив
  ↑ MovementSystem обходит Position+Velocity → кэш-попадания
```

### Паттерн: Strategy (стратегии boids)

Разные типы юнитов имеют разные параметры boids. Вместо условных проверок типа `if (unit_type == CAVALRY)` внутри горячего цикла, мы используем паттерн Strategy через BoidComponent: каждый юнит хранит свои веса и радиус восприятия, и BoidSystem обрабатывает все юниты одинаково, используя данные из компонента.

### Паттерн: Flyweight (общие данные через компоненты)

Компоненты с одинаковыми параметрами (например, все пехотинцы имеют одинаковые веса boids) используют паттерн Flyweight: общий BoidComponent хранится один раз, а все пехотинцы ссылаются на него. Это экономит память и улучшает кэш-локальность: вместо 5000 копий BoidComponent мы храним одну.

### Паттерн: Object Pool (пул сущностей и компонентов)

Мы не создаём и не уничтожаем сущности каждый кадр. Вместо этого при старте демо выделяется пул на максимальное количество сущностей (например, 50 000), и «создание» юнита — это просто активация заранее выделенного слота. «Уничтожение» — это деактивация и возврат в пул. Это устраняет аллокации в горячем цикле.

### Паттерн: Double Buffer (двойной буфер для GPU→CPU)

Для обратной связи GPU→CPU мы используем двойной буфер: GPU пишет в буфер A, пока CPU читает из буфера B. На следующем кадре буферы меняются местами. Это устраняет блокировки и гарантирует, что GPU и CPU никогда не обращаются к одному буферу одновременно.
