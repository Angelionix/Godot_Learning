## 1.1 Концепция и видение

**Жанр:** Симуляция поля битвы / Performance Benchmark

**Ключевая фантазия:** «Полководец, управляющий тысячами» — Игрок наблюдает за масштабным сражением с высоты птичьего полёта, где десять тысяч воинов сталкиваются на поле битвы. Камера скользит над полем, приближаясь к отдельным отрядам или отдаляясь для стратегического обзора. Каждый юнит движется осмысленно: отряды формируют строй, уклоняются от столкновений, атакуют ближайших врагов. Взрывы и заклинания создают тысячи частиц. И всё это работает плавно, без единой просадки.

**Целевая длительность сессии:** 5–15 минут интерактивного исследования. Игрок запускает демо, регулирует параметры (количество юнитов, скорость симуляции, режимы поведения) и наблюдает результат. Сессия не имеет «конца» — это интерактивный бенчмарк, который можно настраивать и изучать. Каждый запуск — это возможность увидеть, как различные техники оптимизации влияют на производительность.

**Почему Performance Demo идеален для финального проекта:** Этот проект не имитирует геймплей ради геймплея — он решает реальную инженерную задачу. Разработчики RTS-игр, симуляторов толпы и масштабных RPG регулярно сталкиваются с необходимостью обрабатывать тысячи сущностей. Наше демо — это практическое руководство по решению этой задачи в Godot Engine. Каждый раздел проекта соответствует реальному узкому месту, с которым вы столкнётесь в коммерческой разработке: обновление позиций, рендеринг, AI-поведение, физика, память. Освоив эти техники, вы сможете применять их в любом проекте с высокой нагрузкой.

## 1.2 Основной демонстрационный цикл

Поскольку Performance Demo — это не игра в классическом понимании, а интерактивный бенчмарк, её «игровой цикл» строится вокруг петли «наблюдение → настройка → измерение → анализ». Игрок взаимодействует с демо через камеру и панель параметров, наблюдает за изменениями в реальном времени и анализирует метрики производительности.

```
┌──────────────────────────────────────────────────────────────────┐
│                   ДЕМОНСТРАЦИОННЫЙ ЦИКЛ                          │
│                                                                   │
│   ┌──────────┐     ┌──────────┐     ┌──────────┐                │
│   │ НАБЛЮДЕ- │────▶│ НАСТРОЙ- │────▶│ ИЗМЕРЕ-  │                │
│   │ НИЕ      │     │ КА       │     │ НИЕ      │                │
│   │          │     │          │     │          │                │
│   │ Камера   │     │ Кол-во   │     │ FPS      │                │
│   │ скользит │     │ юнитов   │     │ Frame    │                │
│   │ над      │     │ Скорость │     │ Time     │                │
│   │ полем    │     │ Режим    │     │ Draw     │                │
│   │ боя      │     │ boids    │     │ calls    │                │
│   └──────────┘     └──────────┘     └────┬─────┘                │
│        ▲                                  │                       │
│        │          ┌──────────┐            │                       │
│        └──────────│ АНАЛИЗ   │◀───────────┘                       │
│                   │          │                                     │
│                   │ Сравнить │                                     │
│                   │ с базой  │                                     │
│                   │ Найти    │                                     │
│                   │ узкие    │                                     │
│                   │ места    │                                     │
│                   └──────────┘                                     │
│                                                                   │
│   Цель: 10 000 юнитов при стабильных 60 FPS                     │
│   Измерение: Frame Time ≤ 16.67 мс                               │
└──────────────────────────────────────────────────────────────────┘
```

**Краткосрочный цикл (секунды):** Изменить параметр → увидеть результат → проверить FPS. Этот микроцикл происходит мгновенно: игрок двигает слайдер количества юнитов, и демо тут же отражает изменение в производительности. Визуальная обратная связь — это сам FPS-счётчик и график Frame Time, отображаемые прямо в демо.

**Среднесрочный цикл (минуты):** Переключение между режимами оптимизации — от базового GDScript к C++, от однопоточного к многопоточному, от CPU к GPU. Каждый режим — это отдельный «слой» оптимизации, и игрок может включать/выключать их, наблюдая кумулятивный эффект. Это превращает демо в интерактивный учебник: вы буквально видите, как каждая техника добавляет FPS.

**Долгосрочный цикл (проект):** Полная прогрессия от GDScript-прототипа (2 FPS с 10K MeshInstance3D) до финального C++ демо (238 FPS с ECS + MultiMesh + compute). Это не игровой прогресс, а инженерный — от «не работает» до «работает невероятно быстро».

## 1.3 Спектр оптимизаций: от GDScript к C++

Ключевая идея проекта — последовательное применение оптимизаций, каждая из которых даёт измеримый прирост. Мы не оптимизируем «всё сразу» — мы добавляем техники одну за другой, замеряя результат каждого шага. Это превращает демо в наглядную демонстрацию того, какой вклад вносит каждая техника.

| Этап | Техника | Ожидаемый FPS (10K юнитов) | Прирост |
| --- | --- | --- | --- |
| 0. Базовый GDScript | 10K MeshInstance3D | ~2 FPS | Базовая линия |
| 1. MultiMesh | 1 draw call вместо 10K | ~15 FPS | 7.5x |
| 2. ECS на C++ | Data Locality + Cache | ~40 FPS | 2.7x |
| 3. Многопоточность | Job-система, 8 потоков | ~90 FPS | 2.3x |
| 4. Compute-шейдеры | GPU boids + частицы | ~150 FPS | 1.7x |
| 5. Полная оптимизация | Frustum + LOD + аллокаторы | ~238 FPS | 1.6x |

Каждый этап опирается на предыдущий. Нельзя эффективно распараллелить код, пока данные не организованы в ECS-структуру. Нельзя перенести вычисления на GPU, пока нет инфраструктуры для обмена данными между CPU и GPU. Эта последовательность — не произвольный выбор, а инженерная необходимость, и наш проект демонстрирует это на практике.

## 1.4 Целевые метрики и бюджет кадра

Бюджет кадра — это фундаментальный концепт оптимизации. При целевых 60 FPS каждый кадр должен укладываться в 16.67 миллисекунд. Если хотя бы один кадр превышает этот лимит, игрок ощущает просадку. Поэтому мы строим бюджет кадра — распределение доступного времени по подсистемам.

### Бюджет кадра (целевой: 60 FPS = 16.67 мс)

| Подсистема | Бюджет | Фактическое время | Запас |
| --- | --- | --- | --- |
| Обновление позиций (ECS + Job) | 2.0 мс | 0.3 мс | 85% |
| Boids AI (compute-шейдер) | 1.0 мс | 0.15 мс | 85% |
| Рендеринг (3 MultiMesh) | 2.0 мс | 0.8 мс | 60% |
| Frustum culling + LOD | 0.5 мс | 0.1 мс | 80% |
| GPU-частицы | 0.5 мс | 0.1 мс | 80% |
| Godot overhead (физика, ввод) | 3.0 мс | 1.5 мс | 50% |
| Прочее (синхронизация, AI) | 3.0 мс | 1.25 мс | 58% |
| **Итого** | **12.0 мс** | **4.2 мс** | **65%** |

Общий запас в 65% (4.2 мс из 16.67 мс) означает, что демо с запасом укладывается в бюджет 60 FPS и может обрабатывать до 30–40K юнитов на мощном железе при сохранении целевого FPS.

### Формула масштабирования

Ключевая формула для расчёта максимального количества юнитов при заданном FPS:

```
max_units = target_fps × frame_budget_ms / time_per_unit_ms

Где:
  time_per_unit_ms = время обновления одного юнита за кадр
  Для ECS + Job: time_per_unit = 0.3 мс / 10 000 = 0.00003 мс/юнит
  Для GDScript:  time_per_unit = 120 мс / 10 000 = 0.012 мс/юнит

Пример (60 FPS, бюджет 12 мс):
  C++ оптимизировано: 60 × 12 / 0.00003 = 24 000 000 юнитов (теоретический предел CPU)
  GDScript:           60 × 12 / 0.012    = 60 000 юнитов (недостижимо из-за overhead)
```

Практический предел определяется не временем обновления позиций, а рендерингом (GPU) и пропускной способностью памяти. Реалистичный максимум для нашего демо — 30–40K юнитов при 60 FPS на GTX 1060.

## 1.6 Система boids и поведение юнитов

Алгоритм boids (bird-oid object) — это классическая модель группового поведения, идеально подходящая для симуляции тысяч юнитов. Каждый юнит (boid) следует трём правилам, создавая реалистичное стадное поведение без центрального координатора.

### Три правила boids

| Правило | Формула | Вес | Эффект |
| --- | --- | --- | --- |
| Разделение (Separation) | steer += normalize(my_pos - neighbor_pos) / dist | 1.5 | Избегание столкновений с ближайшими соседями |
| Выравнивание (Alignment) | steer += normalize(avg_neighbor_velocity) | 1.0 | Движение в направлении соседей |
| Сплочённость (Cohesion) | steer += normalize(avg_neighbor_pos - my_pos) | 0.8 | Движение к центру группы |

**Итоговый вектор руления:**

```
steer = separation × 1.5 + alignment × 1.0 + cohesion × 0.8
velocity += steer × delta
velocity = clamp(velocity, 0, max_speed)
position += velocity × delta
```

### Параметры boids по типам юнитов

| Параметр | Пехотинец | Кавалерист | Лучник |
| --- | --- | --- | --- |
| Макс. скорость | 3.0 ед/с | 5.0 ед/с | 2.5 ед/с |
| Радиус восприятия | 5.0 ед | 6.0 ед | 8.0 ед |
| Радиус разделения | 1.5 ед | 2.0 ед | 2.0 ед |
| Вес разделения | 1.5 | 1.8 | 1.2 |
| Вес выравнивания | 1.0 | 0.8 | 1.2 |
| Вес сплочённости | 0.8 | 0.6 | 1.0 |

### Оптимизация поиска соседей

Прямолинейная реализация boids имеет сложность O(n²), потому что каждый boid проверяет расстояние до всех остальных. Для 10K юнитов это 100 000 000 проверок за кадр — неприемлемо. Мы используем пространственное хеширование (spatial hashing), которое разбивает пространство на ячейки и позволяет каждому boid проверять только соседние ячейки.

| Метод | Сложность | Проверок для 10K | Время (C++) |
| --- | --- | --- | --- |
| Brute force | O(n²) | 100 000 000 | ~45 мс |
| Spatial hashing | O(n × k) | ~300 000 (k≈30) | ~0.5 мс |
| GPU + spatial hash | O(n × k) / GPU | параллельно | ~0.15 мс |

Размер ячейки хеш-таблицы = радиус восприятия (5.0 единиц). Каждый boid проверяет 27 ячеек (3×3×3 окрестность в 3D, или 9 в 2D), что при средней плотности 10K юнитов на площади 100×100 единиц даёт ~30 соседей на boid.

Поскольку Performance Demo — это интерактивный бенчмарк, визуальная обратная связь критически важна. Игрок должен видеть не только сами юниты, но и метрики производительности в реальном времени.

### HUD производительности

| Элемент | Позиция | Содержание |

| Frame Time график | Верхний правый угол | График времени кадра за последние 120 кадров |

### Визуальные маркеры
