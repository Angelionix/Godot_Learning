## 6.2 Методология бенчмаркинга

Правильный бенчмаркинг — это не просто «запустил и посмотрел FPS». Без методологии результаты будут невоспроизводимыми и вводящими в заблуждение.

### Правила бенчмаркинга

1. **Прогрев (warmup):** Первые 60-120 кадров нестабильны — JIT-компиляция, заполнение кэшей, инициализация GPU. Пропускайте их при замерах.

2. **Многократные запуски:** Один запуск — случайность. Проводите минимум 5 запусков и вычисляйте среднее и стандартное отклонение.

3. **Стандартное отклонение:** Если σ > 10% от среднего, результаты ненадёжны. Ищите источник нестабильности (thermal throttling, фоновые процессы).

4. **Release-сборка:** Никогда не бенчмаркьте Debug-сборку. Флаги `-O2` или `-O3` дают 2-5× разницу.

5. **Закрытые приложения:** Браузеры, IDE, стриминг — всё это конкурирует за CPU и память.

6. **VSync выключен:** VSync ограничивает FPS до частоты монитора (60/144), маскируя реальные результаты.

### Код для бенчмаркинга

```cpp
// src/utils/benchmark.h
#pragma once
#include <chrono>
#include <vector>
#include <cmath>
#include <algorithm>
#include <string>

struct BenchmarkResult {
    std::string name;
    double mean_ms;
    double std_dev_ms;
    double min_ms;
    double max_ms;
    int samples;
};

class BenchmarkTimer {
    std::chrono::high_resolution_clock::time_point start_;
    std::string name_;
    int warmup_frames_;
    int measure_frames_;
    std::vector<double> times_;
    int frame_count_ = 0;

public:
    BenchmarkTimer(std::string name, int warmup = 60, int measure = 300)
        : name_(std::move(name)),
          warmup_frames_(warmup),
          measure_frames_(measure) {
        times_.reserve(measure);
    }

    void begin_frame() {
        start_ = std::chrono::high_resolution_clock::now();
    }

    void end_frame() {
        auto end = std::chrono::high_resolution_clock::now();
        double ms = std::chrono::duration<double, std::milli>(end - start_).count();
        ++frame_count_;

        if (frame_count_ > warmup_frames_) {
            times_.push_back(ms);
        }
    }

    BenchmarkResult result() const {
        BenchmarkResult r;
        r.name = name_;
        r.samples = static_cast<int>(times_.size());

        if (times_.empty()) {
            r.mean_ms = r.std_dev_ms = r.min_ms = r.max_ms = 0.0;
            return r;
        }

        double sum = 0.0;
        r.min_ms = times_[0];
        r.max_ms = times_[0];
        for (double t : times_) {
            sum += t;
            r.min_ms = std::min(r.min_ms, t);
            r.max_ms = std::max(r.max_ms, t);
        }
        r.mean_ms = sum / times_.size();

        // Стандартное отклонение
        double var_sum = 0.0;
        for (double t : times_) {
            double diff = t - r.mean_ms;
            var_sum += diff * diff;
        }
        r.std_dev_ms = std::sqrt(var_sum / times_.size());

        return r;
    }

    bool is_complete() const {
        return frame_count_ >= warmup_frames_ + measure_frames_;
    }
};
```

<Callout type="warning" title="Подводные камни бенчмаркинга">
**GC-паузы:** GDScript использует Garbage Collector, который может вызвать скачок frame time. Замечайте такие скачки (выбросы > 3σ) и исключайте их.

**Thermal throttling:** При длительном бенчмарке процессор может перегреться и снизить частоту. Следите за температурой или ограничивайте длительность замера (5-10 секунд).

**Power management:** На ноутбуках профиль питания влияет на частоту CPU. Используйте профиль «Высокая производительность».
</Callout>

## 6.4 Разбивка frame time по системам

При 10 000 сущностях полная оптимизированная версия тратит 4.2 мс на кадр. Вот разбивка:

| Система | Время (мс) | % кадра | Параллелизация |
| --- | --- | --- | --- |
| MovementSystem | 0.8 | 19% | Да (8 потоков) |
| BoidSystem | 1.4 | 33% | GPU / CPU fallback |
| CombatSystem | 0.5 | 12% | Да (через SpatialHash) |
| RenderSystem | 0.6 | 14% | Нет (Godot API) |
| FrustumCulling + LOD | 0.3 | 7% | Нет (нужен Camera3D) |

Узкое место — BoidSystem (33% кадра). Это ожидаемо: boid-система требует поиска соседей для каждой сущности, что даже с SpatialHash является самой тяжёлой операцией.

## 6.5 Тест масштабируемости

Как система ведёт себя при увеличении числа сущностей? Идеально — линейный рост (O(n)). На практике наблюдаются нелинейные эффекты из-за кэш-промахов и конкуренции за память.

| Сущности | Frame time (мс) | FPS | Память (MB) |
| --- | --- | --- | --- |
| 1 000 | 0.5 | 2000 | 2.4 |
| 5 000 | 2.1 | 476 | 12.0 |
| 10 000 | 4.2 | 238 | 24.0 |
| 20 000 | 9.8 | 102 | 48.0 |
| 40 000 | 22.4 | 45 | 96.0 |

При 40K сущностей frame time растёт быстрее, чем линейно (22.4 мс вместо ожидаемых 16.8 мс). Это объясняется кэш-эффектами: при 40K сущностей массивы компонентов превышают размер L3-кэша (обычно 16-32 MB), и начинаются кэш-промахи.

## 6.7 Сравнение с другими движками

Как наш результат (238 FPS при 10K сущностях) соотносится с аналогичными реализациями?

| Движок / Подход | Сущности | FPS | Архитектура |
| --- | --- | --- | --- |
| Unity DOTS (ECS) | 10K | ~300 | C# ECS + Burst Compiler + Job System |
| Unity (MonoBehaviour) | 10K | ~5 | OOP, GameObject per unit |
| Unreal Engine (Niagara) | 10K | ~200 | GPU particles + Niagara |
| Unreal Engine (Actor per unit) | 10K | ~3 | OOP, AActor per unit |
| Godot GDScript (Node3D per unit) | 10K | ~2 | OOP, Node per unit |

Наш результат конкурентоспособен с Unity DOTS и значительно превосходит наивные подходы (Actor per unit в Unreal, Node per unit в Godot). Разрыв с Bevy объясняется zero-cost abstractions Rust и более эффективным rendering backend (wgpu).

## 6.8 Performance HUD

Performance HUD — визуальная панель, отображающая ключевые метрики в реальном времени. Она реализована как C++ узел PerfMonitor с CanvasLayer для overlay.

```gdscript
# scripts/performance_hud.gd
extends CanvasLayer

@onready var fps_label: Label = $VBox/FPSLabel
@onready var frame_label: Label = $VBox/FrameLabel
@onready var entity_label: Label = $VBox/EntityLabel
@onready var system_label: Label = $VBox/SystemLabel

var frame_times: PackedFloat64Array = []
var max_samples: int = 60

func _process(delta: float) -> void:
    # Обновляем метрики
    frame_times.append(delta)
    if frame_times.size() > max_samples:
        frame_times.pop_front()

    var avg_time := 0.0
    var max_time := 0.0
    for t in frame_times:
        avg_time += t
        if t > max_time:
            max_time = t
    avg_time /= frame_times.size()

    var fps := 1.0 / avg_time if avg_time > 0.0 else 0.0
    var frame_ms := avg_time * 1000.0
    var worst_ms := max_time * 1000.0

    fps_label.text = "FPS: %.0f" % fps
    fps_label.add_theme_color_override(
        "font_color", Color.GREEN if fps > 55 else
                      Color.YELLOW if fps > 30 else Color.RED)

    frame_label.text = "Frame: %.2fмс (worst: %.2fмс)" % [frame_ms, worst_ms]

    # Данные от ECSWorld (через сигнал или прямой вызов)
    var ecs_world = get_node_or_null("/root/BattlefieldDemo/ECSWorld")
    if ecs_world:
        entity_label.text = "Сущности: %d" % ecs_world.get_alive_count()
```

<Insight title="Профилирование в разработке vs продакшене">
В разработке HUD показывает всё: FPS, frame time, draw calls, память. В продакшене HUD отключается, но телеметрия собирается: средний FPS, 1st/99th percentile frame time, количество крешей. Инструменты вроде Tracy, RenderDoc и Godot Profiler незаменимы в разработке, но слишком тяжёлые для продакшена.
</Insight>
