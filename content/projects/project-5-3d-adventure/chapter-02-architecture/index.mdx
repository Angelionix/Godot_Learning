## 2.1 Обзор архитектуры (4 слоя)

Архитектура 3D-приключения строится на четырёх слоях, каждый из которых имеет чёткую зону ответственности. Особенность этого проекта — C++ играет основную роль в Logic и Presentation слоях, а GDScript доминирует в Data и Persistence. Это осознанный выбор: C++ обеспечивает производительность для физических подсистем, GDScript — удобство для данных и UI.

**Data Layer (Слой данных):** ItemData, QuestData, QuestObjective, DialogueData, DialogueLine, DialogueChoice, EnemyData, NPCData — все наследуют Resource и используют @export для настройки в редакторе. Никакой логики, только данные. Ресурсы создаются на GDScript для удобства редактирования в инспекторе Godot. C++ код читает эти ресурсы через GDExtension API.

**Logic Layer (Слой логики):** Глобальные менеджеры и C++ контроллеры. GameManager (состояние игры, пауза, регистрация игрока — GDScript Autoload), AdventureCharacter (контроллер персонажа — C++), CameraController (камера — C++), CombatController (бой — C++), NPCController (AI — C++), InventorySystem (инвентарь — C++), QuestSystem (квесты — C++), DayNightCycle (день/ночь — C++), EconomyManager (экономика — GDScript Autoload), AudioManager (звук — GDScript Autoload). Все менеджеры общаются через сигналы, обеспечивая слабую связанность.

**Presentation Layer (Слой представления):** Player, NPC scenes, Enemy scenes, PickableItem, HUD, DialoguePanel, InventoryUI, QuestLogUI, CraftingPanel — все визуальные компоненты. Этот слой отображает данные из Data Layer и реагирует на сигналы из Logic Layer, но не содержит бизнес-логики. HUD обновляет полоску здоровья, когда получает сигнал health_changed, но не вычисляет урон самостоятельно.

**Persistence Layer (Слой хранения):** SaveManager (Autoload) — сериализует состояние игры в JSON, десериализует при загрузке. Каждый менеджер предоставляет методы get_save_data() и load_save_data(), а SaveManager координирует процесс, собирая данные от всех менеджеров в единую структуру. InventorySystem.to_dict() конвертирует C++ структуры в Dictionary для совместимости с Godot.

Дерево сцен — визуальное представление архитектуры. Каждая сцена инкапсулирует свою функциональность и открывает только необходимые интерфейсы (сигналы, методы). Ниже приведены полные деревья для всех ключевых сцен проекта.

## 2.5 Паттерны проектирования

Проект использует следующие паттерны, каждый из которых решает конкретную задачу:

### Конечный автомат (FSM) — NPCController

NPCController использует FSM для управления поведением NPC. Каждое состояние (Idle, Patrol, Follow, Flee, Attack, Stunned) реализует методы `enter()`, `update()` и `exit()`. Переходы управляются условиями: расстояние до игрока, уровень здоровья, наличие линии видимости. Реализация в C++ обеспечивает быстрое переключение для 10–20 NPC одновременно без падения FPS.

```
Idle ──(игрок в detect_range)──▶ Follow ──(игрок в attack_range)──▶ Attack
 ▲                                  │                                  │
 │                                  │(HP < 20%)                        │(игрок ушёл)
 │                                  ▼                                  │
 │                              Flee ◀───────────────────────────────┘
 │                                  │
 │  (игрок вышел из detect_range)   │(достиг точки бегства)
 │                                  ▼
 └──────────────────────────── Idle/Patrol
```

### Strategy — CombatController для комбо

CombatController использует паттерн Strategy для комбо-цепочек. Разные оружия определяют разные последовательности ударов: меч — 3 лёгких + 1 тяжёлый, лук — быстрые выстрелы. Стратегия комбо определяется экипированным оружием и может быть заменена без изменения CombatController.

### Observer — QuestSystem и диалоги

QuestSystem реализует паттерн Observer: диалоговые триггеры подписаны на сигнал `quest_state_changed`, NPC обновляют доступные реплики при изменении состояния квеста. Это слабосвязанная архитектура: квестовая система не знает о конкретных NPC, а NPC не знают о внутренней логике квестов.

### Data-View — ресурсы и UI

Все данные определены как Resource (Data), а UI (View) подписан на сигналы об их изменении. InventoryPanel обновляется при сигнале `inventory_changed`, но не знает, откуда пришли предметы. DialoguePanel отображает DialogueData, но не проверяет условия — это делает C++ код.

### Factory — создание предметов и врагов

Предметы создаются фабричным методом: `ItemFactory.create_item(item_id)` загружает соответствующую сцену из ItemData.world_scene и настраивает параметры. Враги создаются `EnemySpawner.spawn(enemy_data)` на основе EnemyData. Фабрика изолирует создание объектов от бизнес-логики.
